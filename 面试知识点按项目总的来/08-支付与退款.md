# 08 支付与退款（真实接了支付宝沙箱，E2E 跑通过）

## 支付全链路（先背图）

```
前端"去支付" ─► POST /pay/create ─► payment服务:
                                     Feign查order(金额以order为准) → 状态校验(status=0)
                                     → 建/复用支付单 → 调支付宝生成收银台表单HTML
                                            │
用户在支付宝付款 ✔                            ▼
                                     前端跳转支付宝收银台
支付宝服务器 ──POST──► /pay/notify (网关白名单免JWT, 经内网穿透到本地)
                        │
                        ▼  回调四关:
              ①RSA2验签 → ②notify_id唯一索引幂等 → ③app_id/状态/金额校验 → ④CAS 0→1
                        ▼
              Feign 通知 order.markPaid (CAS 0→1)  失败→定时对账补
```

## 知识点 1：创建支付单——"金额权威来源"与幂等复用

**【面试怎么问】** 支付金额能信前端传的吗？用户重复点"去支付"怎么办？

**【项目代码】** `PaymentServiceImpl.create()`：

```java
// ③.5 ⭐ 金额权威来源: 用 order 服务返回的 totalAmount, 绝不用前端传的任何金额
BigDecimal amount = order.getTotalAmount();

// ④ 幂等复用: 该订单已有"待支付"单就复用旧单号, 不重复建
Payment existing = paymentMapper.selectOne(qw);  // WHERE order_id=? AND status=0 LIMIT 1
String paymentNo = (existing != null) ? existing.getPaymentNo() : genPaymentNo(userId);
// 支付宝按 out_trade_no(=paymentNo) 识别交易, 同号自动认成同一笔, 天然不会重复扣钱
```

**【讲解】**
- **前端只传 orderId，金额由后端查 order 服务获得**——前端传金额 = 把改价权交给用户（抓包改成 0.01 元）。这是支付安全的第一原则。
- 状态校验：只有待付款(0)的订单能发起支付，已付/已取消全部拒绝。
- 重复点击复用同一个 paymentNo：支付宝把 out_trade_no 相同的请求认作同一笔交易，配合前面的复用逻辑，怎么点都只会付一次钱。

**【一分钟回答】** 创建支付单三个安全点：金额只认 order 服务返回值，前端传参一律不信；订单状态必须是待付款；同订单未支付时复用已有支付单号——支付宝按 out_trade_no 幂等，重复点击不会重复扣款。

## 知识点 2：异步回调四道关（本项目最完整的安全纵深）

**【面试怎么问】** 支付宝回调怎么处理？怎么防伪造？重复通知怎么办？

**【项目代码】** `PaymentServiceImpl.handleNotify()`：

```java
// ── 第1关: RSA2验签 —— 防伪造"支付成功"的POST白拿货
boolean signOk = AlipaySignature.rsaCheckV1(params, props.getAlipayPublicKey(), ...);
if (!signOk) return "failure";

// ── 第2关: 幂等 —— notify_id 唯一索引当"去重闸"
PaymentNotifyLog logRow = new PaymentNotifyLog();   // 通知原文落库(黑匣子)
logRow.setNotifyId(notifyId);
try {
    notifyLogMapper.insert(logRow);
} catch (DuplicateKeyException dup) {
    return "success";   // 处理过了, 回success让支付宝别再发
}

// ── 第3关: 业务校验 —— app_id是自己的 / 只认TRADE_SUCCESS / 金额和建单一致
if (notifyAmount.compareTo(payment.getAmount()) != 0) {
    log.error("金额不一致! 防改小金额篡改");
    return "failure";
}

// ── 第4关: CAS 0→1 + 通知order (即便前面被绕过, WHERE status=0 也只生效一次)
applyPaid(payment, tradeNo);
return "success";
```

**【讲解】**（每关防什么要说得出来）
1. **验签**：回调端点在网关白名单免 JWT（支付宝没有我们的 token），安全全靠 RSA2——用支付宝公钥验证参数签名，伪造者没有支付宝私钥签不出合法签名。
2. **幂等**：支付宝为保送达会重复通知同一 notify_id。用"插入唯一索引"当原子判重（比先查后插无竞态），顺便把通知原文永久留档，出纠纷有据可查。
3. **业务校验**：app_id 防串应用；金额比对防篡改；非成功态回 success 但不处理（免得支付宝重发垃圾通知）。
4. **CAS**：`WHERE status=0` 是第四道独立防线，前三关全被绕过也只能生效一次。
- 返回值协议：`"success"` 纯文本告诉支付宝"收到别发了"，其他任何返回它都会按 4m/10m/... 间隔重发 —— 所以"处理过的重复通知"也要回 success。

**【一分钟回答】** 回调四关：RSA2 验签防伪造（免鉴权端点的唯一防线）、notify_id 唯一索引防重复通知（插入即判重+留档）、app_id/交易状态/金额三项业务校验防篡改、最后 CAS 条件更新兜底保证只生效一次。处理完回文本 success 停止重发。

## 知识点 3：回调不可靠时的主动查询兜底

**【面试怎么问】** 回调丢了（网络问题/内网环境收不到）用户付了钱但订单没变化怎么办？

**【项目代码】** `PaymentServiceImpl.queryStatus()`（前端轮询接口）：

```java
// DB 还是待支付时, 别干等异步回调 —— 主动调 alipay.trade.query 问支付宝
if (payment.getStatus() == 0) {
    queryAndSyncFromAlipay(payment);   // 已付 → 走 applyPaid (和回调完全同一套落库代码)
    payment = getByPaymentNo(payment.getPaymentNo());
}
```

**【讲解】**
- 支付状态的三条同步通道互为备份：**异步回调（主）→ 前端轮询触发主动查询（补）→ 定时对账（兜底）**。
- 关键设计：主动查询和回调**共用 `applyPaid()` 一个落库出口**——CAS 保证两条路并发也只生效一次，且行为完全一致。多入口单出口是幂等设计的好习惯。
- 开发时的真实背景：本地环境支付宝回调打不进来，先靠主动查询跑通；后来用 natapp 内网穿透把 `/pay/notify` 暴露到公网才测通真回调——这段经历可以讲"我理解回调类集成的联调难点"。

**【一分钟回答】** 三通道收敛：异步回调为主；前端轮询状态接口时若仍待支付就主动调 alipay.trade.query 补一次；再往后有定时对账。三条路共用同一个 CAS 落库方法，并发/重复都只生效一次。

## 知识点 4：两段式退款审批（状态机跨三张表编排）

**【面试怎么问】** 退款流程怎么设计的？为什么不用户一点就退？

**【项目代码】** 第一段 `RefundServiceImpl.apply()`（用户申请，**不碰钱**）：

```java
// 建退款单 status=0 待客服审批 —— 不再当场调支付宝
refund.setStatus((byte) 0);
refundMapper.insert(refund);

// 通知 order: 1/2 → 5(申请退款中), 并拿回"退款前原状态"
Result<Integer> r = orderFeignClient.markRefundApplying(payment.getOrderId());
Integer preStatus = r.getData();          // 1已付款 或 2已发货
refund.setPreOrderStatus(preStatus);      // ⭐ 存下来, 客服拒绝时按它回滚
```

第二段 `approve()`（客服批准，才真退钱）：

```java
resp = alipayClient.execute(request);     // alipay.trade.refund 同步接口
if (resp.isSuccess() && "Y".equals(resp.getFundChange())) {   // fund_change=Y 才是真退了钱
    refund.setStatus((byte) 2);           // 退款单→成功
    // 支付单 CAS 1→4已退款; 通知order 5→6已退款(回补库存+退券在order侧)
} else {
    markRefundFailed(refund, msg);
    rollbackOrderAfterFailedRefund(refund);   // ⭐ 退款失败订单回到原状态, 不能卡死在5
}
```

**【讲解】**
- 两段式的业务动机：**钱的操作必须有人审**（防恶意退款/薅羊毛），架构动机：把"登记意图"和"执行资金操作"分离，每段各自幂等可重试。
- `pre_order_status` 是精髓：申请时把订单原状态（已付款还是已发货）存进退款单，拒绝/失败时能**精确回滚**到原状态，而不是拍脑袋回到某个默认态。
- 每个失败分支都有出路：调支付宝异常→退款单标失败+订单回滚；`fund_change != Y`→同样处理——订单绝不会永久卡在"申请退款中"。
- 状态机全景（三张表联动）：`refund: 0待审批→2成功/3失败/4拒绝`，`payment: 1已支付→4已退款`，`orders: 1/2→5申请中→6已退款(批准) 或 →回原状态(拒绝)`。

**【一分钟回答】** 两段式：用户申请只建退款单（待审批）并把订单 CAS 到"申请退款中"，同时记下原状态；客服批准才调支付宝真退款，成功后三张表按状态机联动（退款单成功、支付单已退款、订单已退款+回库存+退券），拒绝或退款失败都按记录的原状态精确回滚，订单不会卡死。

## 附：联调用到的工程技能（面试聊天素材）

- **内网穿透**：支付宝回调必须打到公网地址，本地开发用 natapp 隧道 `公网域名 → 127.0.0.1:9080`，回调 URL 用环境变量 `${ALIPAY_NOTIFY_URL:默认值}` 覆盖，零代码改动切换环境。
- **配置分离**：支付宝私钥/APPID 在 gitignored 的 application.yml 里，仓库只提交 application.yml.example 模板——密钥绝不进 git。
- **验证链路的方法**：payment_notify_log 表里 verify_result=1 证明验签通过、notify_id 留档证明幂等生效——用数据自证系统行为，不是"我觉得没问题"。
