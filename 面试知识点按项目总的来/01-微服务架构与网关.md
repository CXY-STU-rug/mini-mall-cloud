# 01 微服务架构与网关

## 知识点 1：服务注册与发现（Nacos）

**【面试怎么问】** 微服务之间怎么找到对方？Nacos 的作用是什么？

**【项目代码】** `mini-mall-gateway/src/main/resources/application.yml`

```yaml
spring:
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848   # 每个服务启动时把"服务名+IP+端口"注册到这里

    gateway:
      routes:
        - id: user-route
          uri: lb://mini-mall-user    # lb = LoadBalancer, 按服务名去 Nacos 查健康实例
          predicates:
            - Path=/user/**           # 路径前缀匹配
```

**【讲解】**
- 每个服务的 yml 里都配了 `nacos.discovery.server-addr`，启动时向 Nacos 注册自己，并定时发心跳；心跳断了 Nacos 会把实例摘掉。
- `lb://mini-mall-user` 里的 `lb` 是关键：网关不写死 IP，而是拿服务名去 Nacos 查健康实例列表，再由 LoadBalancer 按轮询挑一个转发。**服务扩容/换机器，调用方零改动**。
- 项目早期（D2 阶段）路由写的是 `http://localhost:9001` 硬编码，E2 阶段才改成 `lb://`——这个演进本身就是面试好素材："我体会过硬编码的痛，才理解注册中心解决了什么"。

**【一分钟回答】** 服务启动时把自己注册到 Nacos 并维持心跳；调用方（网关的 lb://、Feign 的服务名）不关心 IP，运行时从 Nacos 拉健康实例列表做客户端负载均衡。好处是扩缩容、故障摘除对调用方透明。

## 知识点 2：网关的职责与过滤器链

**【面试怎么问】** 你们网关做了什么？过滤器执行顺序怎么控制？

**【项目代码】** 网关三个过滤器，靠 `Ordered` 接口的返回值排序（数字越小越先执行）：

```
RequestLogFilter(-150) → AuthGlobalFilter(-100) → SentinelGatewayFilter(0) → 路由转发(10000+)
     生成traceId              JWT鉴权                  限流
```

`mini-mall-gateway/.../filter/RequestLogFilter.java`：

```java
@Component
public class RequestLogFilter implements GlobalFilter, Ordered {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        // 8 位短 traceId, 塞进 header 透传给下游, 跨服务日志能串起来
        String traceId = UUID.randomUUID().toString().substring(0, 8);
        ServerHttpRequest mutated = request.mutate().header("X-Trace-Id", traceId).build();
        log.info("[{}] -> {} {}", traceId, request.getMethod(), request.getURI().getPath());
        return chain.filter(exchange.mutate().request(mutated).build());
    }
    @Override
    public int getOrder() { return -150; }   // 必须比鉴权(-100)先跑: 401 的攻击请求也要留日志
}
```

**【讲解】**
- 网关职责三件事：**统一入口路由**（18 条 route）、**统一鉴权**（JWT 只在网关解一次，下游不用重复解）、**统一限流**（Sentinel 按路由 ID 限流）。
- 日志过滤器为什么排最前（-150）：如果排在鉴权后面，被 401 拦掉的请求就没有日志，出了安全事件查不到"谁在攻击"。
- **traceId 为什么放 header 不放 ThreadLocal**：网关是 WebFlux 异步模型，一个请求会在多个 EventLoop 线程间漂移，ThreadLocal 会丢；HTTP header 能稳定跨线程、跨进程透传。
- 过滤器 order 不是摆设——本项目踩过真实的坑：Sentinel 过滤器默认排在链头，和鉴权过滤器写响应产生竞态，导致限流时客户端收到"裸 200 空响应"（详见 [11-可观测性与调试实战.md](11-可观测性与调试实战.md)）。

**【一分钟回答】** 网关做路由、鉴权、限流三件事。全局过滤器实现 GlobalFilter + Ordered，order 越小越先执行；我们的链是日志(-150)→鉴权(-100)→限流(0)→路由。顺序是设计出来的：日志最前保证攻击留痕，限流放鉴权后是因为踩过响应写竞态的坑。

## 知识点 3：WebFlux 网关 vs 传统 Servlet（为什么网关代码长得不一样）

**【面试怎么问】** Spring Cloud Gateway 为什么基于 WebFlux？和你业务服务里的 Interceptor 有什么区别？

**【项目代码】** 对比项目里两段"做同样事情"的代码：

```java
// 网关 AuthGlobalFilter (WebFlux 响应式): 返回 Mono<Void>, 用 exchange 操作请求
public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
    return reactiveRedis.hasKey(BLACKLIST_PREFIX + jwt)   // 查 Redis 也是异步的
            .flatMap(inBlacklist -> { ... return chain.filter(exchange); });
}

// 业务服务 HeaderInterceptor (Servlet 同步): 返回 boolean, 用 HttpServletRequest
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    String userId = request.getHeader(HEADER_USER_ID);
    SecurityContextHolder.setUserId(userId);   // ThreadLocal 在同步模型里是安全的
    return true;
}
```

**【讲解】**
- 网关是纯 IO 转发场景（不做重业务），WebFlux + Netty 少量线程扛大量并发连接，比"一请求一线程"的 Tomcat 更适合。
- 代价是编程模型变了：不能阻塞、不能用 ThreadLocal、连 Redis 都要用 `ReactiveStringRedisTemplate`。项目 pom 里特意注释了"千万别再引 spring-boot-starter-web，会跟 Servlet 冲突"。
- 业务服务仍是 Spring MVC 同步模型——同步好写好调，网关才需要响应式。**技术选型按场景，不是越新越好**。

**【一分钟回答】** 网关是 IO 密集转发场景，用 WebFlux+Netty 事件循环模型，少量线程扛高并发；业务服务保持 MVC 同步模型方便开发。混用的代价我踩过：网关里必须用 reactive 版 Redis 客户端，ThreadLocal 不能用，身份透传只能靠 header。

## 知识点 4：模块化设计（common 公共包）

**【面试怎么问】** 公共代码怎么复用？多模块 Maven 怎么组织？

**【项目代码】** `mini-mall-common/` 下按职责拆四个子模块：

```
mini-mall-common-core      Result统一返回 / BusinessException / GlobalExceptionHandler / SecurityContextHolder
mini-mall-common-security  JwtUtil / HeaderInterceptor / FeignAuthInterceptor (自动装配)
mini-mall-common-redis     RedisTemplate 序列化配置 / RedisService 封装
mini-mall-common-swagger   接口文档配置
```

`GlobalExceptionHandler` 的一个细节（`common-core/.../GlobalExceptionHandler.java:5`）：

```java
// ⚠️ 不能 import jakarta.servlet.http.HttpServletRequest
// common-core 必须是【纯通用】，绑定 Servlet 会让 WebFlux 网关启动崩溃
```

**【讲解】**
- 拆分原则：**core 不依赖任何 Web 容器**（网关 WebFlux 也要引它）；security 里的 MVC 配置加了 `@ConditionalOnClass`，网关引入时自动跳过 Servlet 相关装配。
- 统一返回 `Result<T>`（code/message/data）+ 全局异常处理器，Controller 里只管 `throw new BusinessException("库存不足")`，格式化是切面的事。
- 异常处理器还藏了一个实战修复：Seata 的 AOP 会把 `BusinessException` 包成 `RuntimeException`，兜底 handler 里循环解包 cause 链找回原始业务异常，否则用户看到的全是"系统繁忙"。

**【一分钟回答】** 公共代码抽成 common 多模块：core（返回体/异常）、security（JWT/拦截器）、redis（序列化）。关键约束是 core 保持零容器依赖，让 Servlet 服务和 WebFlux 网关都能引；条件装配（@ConditionalOnClass）解决"同一个包在不同容器里行为不同"的问题。
