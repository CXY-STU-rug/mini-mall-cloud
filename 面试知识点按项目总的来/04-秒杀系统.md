# 04 秒杀系统（本项目最能打的高并发设计）

## 全链路一张图（先背下来）

```
用户点"抢购"
   │
   ▼
① 活动校验 (时间窗口/活动存在)                    —— MySQL 读一次
   │
   ▼
② Redis Lua 脚本原子执行:                        —— 高并发全在这一步扛住
   检查预热 → 检查已购Set → 检查库存 → DECR库存 + SADD已购
   │  (抢到资格的用户 << 总请求数)
   ▼
③ 发 MQ 消息 (activityId + userId + 地址快照)     —— 削峰
   │
   ▼
④ SeckillOrderListener 异步消费:                  —— 数据库压力被拉平
   幂等检查 → Feign扣真实库存 → 建订单/明细/秒杀记录(本地事务)
   │
   ▼
⑤ 发延迟消息 30 分钟 → 超时未付自动关单回库存
   │
   ▼
前端轮询 querySeckillResult: SUCCESS / PROCESSING / NOT_FOUND
```

核心思想一句话：**把"扣库存"从数据库挪到 Redis（单线程原子），把"写订单"从同步挪到 MQ（异步削峰）**。

## 知识点 1：为什么必须用 Lua 脚本（超卖的根源）

**【面试怎么问】** 怎么防超卖？为什么 Java 里先 GET 再 DECR 不行？

**【项目代码】** `mini-mall-order/src/main/resources/lua/seckill_stock.lua`

```lua
-- KEYS[1]=seckill:stock:{activityId}  KEYS[2]=seckill:bought:{activityId}  ARGV[1]=userId
-- 返回: 1成功 / 0售罄 / -1已抢过 / -2未预热

if redis.call('EXISTS', KEYS[1]) == 0 then return -2 end          -- ① 活动预热检查
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return -1 end  -- ② 防一人多单
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock <= 0 then return 0 end                                    -- ③ 库存检查
redis.call('DECR', KEYS[1])                                        -- ④ 扣减 + 记录
redis.call('SADD', KEYS[2], ARGV[1])
return 1
```

Java 侧调用（`SeckillActivityServiceImpl.seckill()`）：

```java
Long result = stringRedisTemplate.execute(
        seckillStockScript,                        // DefaultRedisScript<Long>, 启动时加载+SHA1缓存
        Arrays.asList(stockKey, boughtKey),
        userId.toString());
if (result == -1L) throw new BusinessException(400, "您已经参与过本次秒杀");
if (result == 0L)  throw new BusinessException(400, "已售罄");
```

**【讲解】**
- 超卖的根源是 **check-then-act 不原子**：Java 里"读到 stock=1 → 判断>0 → DECR"三步之间，另外 999 个线程也读到了 stock=1，全都通过判断 → 库存扣成 -999。
- Lua 脚本在 Redis **单线程里整体原子执行**，"检查已购→检查库存→扣减→记录"四步一气呵成，中途不会被任何客户端打断。
- 防一人多单和防超卖必须在**同一个脚本里**：拆成两次调用又会产生竞态窗口。
- `DefaultRedisScript` Bean（`LuaScriptConfig`）：启动加载一次，Spring 用 EVALSHA 发送 SHA1 而不是每次传整段脚本。

**【一分钟回答】** 库存放 Redis，扣减用 Lua 脚本：检查预热→检查用户已购 Set→检查库存→DECR+SADD 四步在 Redis 单线程里原子完成，不存在 check-then-act 竞态，天然防超卖也防一人多单。返回值区分四种结果让前端给出准确提示。

## 知识点 2：MQ 异步下单（削峰填谷）

**【面试怎么问】** 抢到资格后为什么不直接写订单？MQ 在秒杀里的作用？

**【项目代码】** 生产端（抢到资格才发消息）：

```java
if (result == 1L) {
    SeckillOrderMessage message = new SeckillOrderMessage();   // activityId+userId+地址快照
    ...
    try {
        rabbitTemplate.convertAndSend(SECKILL_EXCHANGE, SECKILL_ROUTING_KEY,
                objectMapper.writeValueAsString(message));
    } catch (JsonProcessingException e) {
        rollbackSeckillQuota(activityId, userId);   // ⭐ 发MQ失败 → 把Redis资格回滚还给别人
        throw new BusinessException(500, "订单排队失败，请稍后再试");
    }
    return "抢购成功，订单正在生成，请稍后查看结果";
}
```

消费端 `SeckillOrderListener.onSeckillMessage()`：

```java
@RabbitListener(queues = RabbitMQConfig.SECKILL_QUEUE)
public void onSeckillMessage(String msg, Message message, Channel channel) throws IOException {
    try {
        // ⭐ 幂等第一步: 查 seckill_order 表, 该用户该活动已有记录 → 重复消息直接跳过
        Long exists = seckillOrderMapper.selectCount(existsWrapper);
        if (exists > 0) { return null; }

        // 本地事务里: Feign扣product真实库存 → 建orders + order_item + seckill_order
        Long orderId = transactionTemplate.execute(status -> createNormalOrder(finalPayload));

        // 建单成功 → 发30分钟延迟消息(超时关单), 然后手动ACK
        rabbitTemplate.convertAndSend(DELAY_EXCHANGE, DELAY_ROUTING_KEY, orderId);
        channel.basicAck(deliveryTag, false);
    } catch (Exception e) {
        // 失败且订单没建成 → 回滚Redis资格(库存+1, 移出已购Set), NACK不重回队列
        if (!orderCreated && payload != null) rollbackSeckillQuota(...);
        channel.basicNack(deliveryTag, false, false);
    }
}
```

**【讲解】**
- **两段库存**的设计要说清：Redis 里的是"秒杀资格库存"（预扣），MySQL product 表是"真实库存"（消费时扣）。Redis 挡掉 99% 的请求，到达数据库的写入速率由消费者决定——这就是削峰。
- 地址快照放进消息体：消费时不再依赖 user 服务查地址（用户抢完就改地址也不影响这单）。
- 失败补偿是闭环：发 MQ 失败回滚资格、消费失败回滚资格、扣了真实库存但建单失败还要 `restoreStock` 回补——**每个失败分支都要把状态退回去**。
- 前端体验：抢购接口立即返回"排队中"，用轮询 `querySeckillResult` 查三态（SUCCESS：查到订单 / PROCESSING：在已购 Set 里但订单还没落库 / NOT_FOUND：没抢到）。

**【一分钟回答】** 抢到 Redis 资格后只发一条 MQ 消息就返回"排队中"，消费者异步做真正的建单+扣真实库存，数据库写入被拉平。每个失败点都有补偿：发消息失败、消费失败都回滚 Redis 资格，扣库存后建单失败回补库存。前端轮询查结果，三态由"订单表+已购 Set"推导。

## 知识点 3：消息幂等（MQ 必然重复投递）

**【面试怎么问】** 消息重复消费怎么办？

**【项目代码】** 消费端的幂等靠"业务唯一性检查"：

```java
// 同一个 (userId, activityId) 只允许一条秒杀记录
QueryWrapper<SeckillOrder> existsWrapper = new QueryWrapper<>();
existsWrapper.eq("user_id", userId).eq("seckill_activity_id", activityId);
if (seckillOrderMapper.selectCount(existsWrapper) > 0) {
    log.warn("[MQ-Seckill] 重复消息跳过");
    return null;   // 第二次消费什么都不做
}
```

**【讲解】**
- RabbitMQ 保证"至少一次"投递：ACK 丢失、消费者重启都会导致重复投递，**幂等是消费者的义务**。
- 幂等三板斧在本项目都有实例：① 业务查重（上面这段）；② 数据库唯一索引兜底（支付回调的 notify_id 唯一键，见 08）；③ CAS 条件更新天然幂等（关单 `WHERE status=0`，第二次 rows=0，见 05/06）。

**【一分钟回答】** MQ 只能保证至少一次投递，幂等必须消费端做。手段按强度：先业务键查重快速跳过，数据库唯一索引做最后兜底，状态类操作直接用条件 UPDATE 天然幂等——同一条消息消费两次，第二次 rows=0 无副作用。

## 知识点 4：秒杀的完整防线清单（面试总结用）

| 层 | 手段 | 项目代码 |
|----|------|---------|
| 网关 | Sentinel 对 seckill-route 限流(100 QPS+50突发) | Nacos `mini-mall-gateway-gw-flow-rules` |
| 资格 | Redis Lua 原子扣减 + 已购 Set 防重 | seckill_stock.lua |
| 削峰 | MQ 异步建单 | SeckillOrderListener |
| 真实库存 | SQL 原子扣减 `UPDATE ... WHERE stock >= qty` | ProductMapper.deductStock |
| 幂等 | 业务查重 + CAS | Listener + closeOrderByMQ |
| 兜底 | 30 分钟延迟关单回库存回资格 | OrderCloseListener |
| 失败补偿 | 每个失败分支回滚 Redis 资格/回补库存 | rollbackSeckillQuota / restoreStock |

**【一分钟回答】** 从外到内：网关限流削掉洪峰 → Redis Lua 原子扣资格（防超卖防重复）→ MQ 异步落库削峰 → 数据库层 `UPDATE...WHERE stock>=qty` 原子扣真库存做最后防线 → 延迟队列关超时单回收库存。每一层被击穿都有下一层兜着。
