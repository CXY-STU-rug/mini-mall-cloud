# 11 可观测性与调试实战

## 知识点 1：SkyWalking 全链路追踪

**【面试怎么问】** 微服务一个请求跨五个服务，怎么排查慢在哪、错在哪？

**【项目部署】**（无侵入，零代码）

```
每个 java 服务启动参数:
  -javaagent:D:\skywalking-agent\skywalking-agent.jar
  -Dskywalking.agent.service_name=mini-mall-order
  -Dskywalking.collector.backend_service=127.0.0.1:11800

后端: OAP(收集分析, gRPC 11800) + UI(18080) + 存储 Elasticsearch
```

**【讲解】**
- 原理：**Java Agent 字节码增强**——JVM 加载类时 agent 修改字节码插入埋点，业务代码零改动。这就是"无侵入 APM"。
- traceId 跨进程透传：HTTP 调用放 header，**RabbitMQ 里放消息 header**——项目实测秒杀"抢购→MQ→异步建单"整条异步链在同一个 trace 里，这个细节很多人不知道。
- 真实用例（能讲）：退款审批的一次请求 trace 里串起 5 个服务 + MySQL/Redis/MQ 的 span；其中支付宝 SDK 调用没被插桩，表现为 span 之间 ~1750ms 的"时间空洞"——**会读 trace 的空洞也是本事**（空洞=未插桩的外部调用或 CPU 计算）。
- 存储演进：默认 H2 内存存储重启即丢，后切到 Elasticsearch，重启 OAP 数据仍在——这也是"我真用过而不是装了个玩具"的证据。

**【一分钟回答】** SkyWalking Java Agent 字节码增强无侵入埋点，traceId 经 HTTP header 和 MQ 消息头跨进程甚至跨异步链路透传，OAP 收集 ES 存储。排查时按 traceId 拉整条调用树看每个 span 耗时，span 间的时间空洞对应未插桩的外部调用。

## 知识点 2：自研 traceId + 分层日志

**【项目代码】** 网关 `RequestLogFilter`（order=-150 最先跑）生成 8 位 traceId 放 `X-Trace-Id` header 透传，每服务日志带上它，grep 一个 id 串起全链路日志。

**【讲解】** SkyWalking 看调用拓扑和耗时，文本日志看业务细节，两者靠 traceId 关联。轻量方案（header 透传）在没上 APM 的团队也普遍适用，两套都会说明理解本质：**上下文跨进程接力**。

## 知识点 3：一次真实的疑难 bug 排查（面试讲故事的王牌）

> 背景：给网关限流做回归测试时发现——**触发限流的请求返回的不是 429 JSON，而是"裸 200 空响应"**。以下按排查过程复盘，这是展示 debug 能力的最好素材。

### 现象
- 限流规则确实生效（超阈值的请求没到下游），但客户端收到 HTTP 200、无 body、无 Content-Type。
- 预期是自定义的 `429 {"code":429,"message":"网关限流..."}`。

### 排查过程（讲的时候突出"控制变量 + 证据链"）

1. **假设一：没配自定义降级响应** → 注册了 `BlockRequestHandler` 输出 JSON，无效。说明异常根本没走到这个回调。
2. **假设二：SkyWalking agent 干扰**（它也做字节码增强）→ **控制实验**：摘掉 agent 重跑，现象不变，排除。
3. **打探针**：加临时 WebFilter 在 `beforeCommit` 钩子里抓栈，发现关键证据——**响应处于"假已提交"状态**：`isCommitted()=true` 但实际 commit 没完成，`setStatusCode(429)` 返回成功却写不进去。
4. **定位根因**：Sentinel 的 `SentinelGatewayFilter` 自动装配时 order=`HIGHEST_PRECEDENCE`（整条链最前）。它包住了会写响应的鉴权过滤器（-100）。限流触发时 Sentinel 的 block-cancel 信号和鉴权路径的响应提交在 Reactor 订阅链上**竞态**，Netty 把一个半截的响应 flush 出去 = 裸 200。
5. **修复尝试的坑**：yml 里 `spring.cloud.sentinel.filter.order: 0` **不生效**——查证：这个配置只对 MVC 版 Sentinel 有效，网关版不读（日志确认 order 仍是 -2147483648）。**"验证自动装配的行为要靠实验，不能只信文档"**。
6. **最终修复**（两件套，`SentinelGatewayConfig.java`）：

```java
// ① 自己注册带 order 的过滤器 Bean, 借 @ConditionalOnMissingBean 顶掉自动装配的:
//    order=0 → 鉴权(-100)之后、路由(10000+)之前, 下游无人在订阅期写响应, 竞态消失
@Bean
public SentinelGatewayFilter sentinelGatewayFilter() {
    return new SentinelGatewayFilter(0);
}

// ② 最高优先级 WebExceptionHandler 接住 BlockException 家族, 直接写 429 JSON
@Bean
@Order(Ordered.HIGHEST_PRECEDENCE)
public WebExceptionHandler sentinelBlockJsonHandler() {
    return (exchange, ex) -> {
        if (!BlockException.isBlockException(ex)) return Mono.error(ex);  // 不是限流异常→放行
        response.setStatusCode(HttpStatus.TOO_MANY_REQUESTS);
        response.getHeaders().setContentType(MediaType.APPLICATION_JSON);
        return response.writeWith(Mono.just(response.bufferFactory().wrap(blockBody(ex))));
    };
}

// ③ BlockRequestHandler 改成纯透传: 不自己写响应(adapter的writeTo在Spring6.1有兼容坑),
//    只把异常抛出去交给上面的 WebExceptionHandler 统一出口
GatewayCallbackManager.setBlockHandler((exchange, throwable) -> Mono.error(throwable));
```

7. **回归验证**：连打 8 次 `/search/product` → 4 次 200 正常 JSON + 4 次 429 自定义 JSON，符合 30 QPS 规则预期；顺手验证了 Nacos 改规则 3→30 免重启生效。
8. **顺带的语义改进**：过滤器后移后，无 token 的请求先被鉴权 401 挡掉、**不再消耗限流配额**——配额留给真实用户，副作用反而更合理。

### 这个故事回答了面试官的什么问题

| 面试官考察点 | 故事中的对应 |
|-------------|------------|
| 遇到疑难 bug 的方法论 | 假设→控制实验→探针取证→根因→修复→回归，完整闭环 |
| 对框架的理解深度 | 过滤器 order、自动装配 @ConditionalOnMissingBean、Reactor 订阅时序 |
| 不迷信文档 | yml 配置对网关版无效是实测出来的 |
| 修复质量意识 | 不是 hack 掉现象，而是消除竞态根因 + 统一异常出口，且做了回归 |

**【一分钟版本】** 网关限流触发时客户端收到裸 200 而非 429。控制实验排除了 SkyWalking，探针抓到响应"假已提交"，根因是 Sentinel 过滤器默认排链头、其 block-cancel 与鉴权过滤器写 401 在响应式订阅链上竞态。yml 改 order 对网关版无效，最终自己注册 order=0 的过滤器 Bean 消除竞态，再用最高优先级 WebExceptionHandler 统一输出 429 JSON，回归通过。
