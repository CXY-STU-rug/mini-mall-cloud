# 02 认证授权与安全设计

## 知识点 1：JWT 的签发与校验

**【面试怎么问】** JWT 是什么结构？和 Session 比优劣？你们怎么用的？

**【项目代码】** `mini-mall-common-security/.../util/JwtUtil.java`

```java
public String generateToken(Long userId, String username, Byte role) {
    Map<String, Object> claims = new HashMap<>();
    claims.put("userId", userId);
    claims.put("username", username);
    claims.put("role", role);              // role 塞进 token, 网关判管理员不用查库
    return Jwts.builder()
            .claims(claims)
            .issuedAt(new Date())
            .expiration(new Date(System.currentTimeMillis() + jwtProperties.getExpiration()))
            .signWith(getSigningKey())     // HMAC-SHA 对称签名
            .compact();                    // 输出 header.payload.signature 三段式
}

public Claims parseToken(String token) {
    return Jwts.parser().verifyWith(getSigningKey())   // 验签不过/过期 → 抛异常
            .build().parseSignedClaims(token).getPayload();
}
```

**【讲解】**
- 三段式 `header.payload.signature`：payload 是 **Base64 编码不是加密**（所以绝不放密码），防篡改靠第三段签名——改了 payload 签名就对不上。
- vs Session：JWT 无状态，服务端不存会话，天然适合微服务（任何实例都能验）；代价是**发出去就收不回**，这个缺陷项目用"登出黑名单"补（见知识点 3）。
- role 塞进 claims 是空间换时间：网关每个请求都要判管理员，查库不现实，解 token 直接拿。
- `@RefreshScope` 配合 Nacos：改 `jwt.secret` 不用重启服务。

**【一分钟回答】** 登录成功用 HMAC 签发 JWT，claims 里带 userId/role，7 天过期。网关统一验签+过期校验，下游服务零成本拿身份。JWT 无状态适合微服务多实例，但"无法主动失效"的缺陷我们用 Redis 黑名单补齐了。

## 知识点 2：网关鉴权的分层设计（白名单 / 黑名单 / 默认拒绝）

**【面试怎么问】** 接口权限怎么控制的？怎么防越权？

**【项目代码】** `mini-mall-gateway/.../filter/AuthGlobalFilter.java`，四层规则从上往下：

```java
// ① 黑名单最先判: 路径含 /internal 的服务间内部接口, 外部一律 403
//    (服务间真正的调用走 Feign+Nacos 直连, 不过网关, 不受影响)
if (isInternal(path)) { return forbidden; }

// ② 白名单: 登录注册、C端只读浏览(GET商品/分类/搜索)、支付宝回调 → 免token放行
private static final List<WhitelistRule> WHITE_LIST = List.of(
        new WhitelistRule("/auth", null),
        new WhitelistRule("/product", Set.of(HttpMethod.GET)),   // 只放 GET!
        new WhitelistRule("/pay/notify", null),   // 支付宝服务器调, 没有JWT, 安全靠RSA2验签
        ...);

// ③ JWT 验签 + Redis黑名单(已登出) + 禁用用户检查

// ④ RBAC: /admin/** 或"非C端白名单的一切写操作"必须 role=1
private boolean needAdmin(String path, HttpMethod method) {
    if (path.startsWith("/admin/")) return true;
    boolean isWrite = method == POST || method == PUT || method == DELETE || method == PATCH;
    if (!isWrite) return false;
    if (isCEndWrite(path)) return false;   // 购物车/订单/评价等"操作自己资源"的写
    return true;   // ⭐ 其余所有写操作 → 默认拒绝, 必须 admin
}
```

**【讲解】**
- 最值得讲的是**默认拒绝（deny by default）**：早期是"枚举哪些接口要 admin"，漏配一个就是漏洞；SEC 阶段反转成"枚举哪些写操作普通用户可做，其余写操作全要 admin"。以后新增接口忘了配 → 表现为报 403 立刻被发现，而不是悄悄留一个谁都能调的洞。
- 白名单带 method 维度：`GET /product` 放行（浏览），`POST /product`（建商品）不放行，自动落进"默认拒绝"要 admin。
- `/pay/notify` 免鉴权不是漏洞：支付宝服务器不可能带我们的 JWT，这个端点的安全由回调内部的 RSA2 验签保证（见 08 支付）。

**【一分钟回答】** 网关四层：internal 接口一律 403 → 白名单（登录/只读浏览/支付回调）放行 → JWT 验签+黑名单 → RBAC。RBAC 的核心是默认拒绝：除了明确列出的 C 端自有资源写操作，一切写操作都要求管理员，漏配表现为 403 而不是漏洞。

## 知识点 3：登出黑名单（JWT 的"无法失效"缺陷怎么补）

**【面试怎么问】** JWT 怎么做登出？用户被封禁怎么即时踢下线？

**【项目代码】** 写入端 `mini-mall-auth/.../AuthController.java`：

```java
@PostMapping("/logout")
public Result<Void> logout(@RequestHeader("Authorization") String authHeader) {
    String token = authHeader.substring(7);
    Claims claims = jwtUtil.parseToken(token);
    // ⭐ TTL = token 剩余有效期: token 自然过期后黑名单自动清, 不占空间
    long ttl = claims.getExpiration().getTime() - System.currentTimeMillis();
    if (ttl > 0) {
        stringRedisTemplate.opsForValue().set("jwt:blacklist:" + token, "1", ttl, TimeUnit.MILLISECONDS);
    }
    return Result.success();
}
```

校验端（网关，reactive）：

```java
return reactiveRedis.hasKey(BLACKLIST_PREFIX + jwt)
        .onErrorReturn(false)      // ⭐ Redis 挂了 → fail-open 降级放行
        .flatMap(inBlacklist -> {
            if (inBlacklist) return unauthorized(exchange);
            // 再查禁用标记 user:disabled:{uid} → 命中 403, 被禁用户旧token立即失效
            ...
        });
```

**【讲解】**
- 黑名单 key 的 TTL 设计是亮点：**恰好等于 token 剩余寿命**，过期自动清理，黑名单永远不会膨胀。
- `onErrorReturn(false)` 是一个明确的**取舍决策（fail-open）**：Redis 挂了时宁可暂时失去黑名单校验，也不能让所有登录请求 500 整站瘫痪。面试说出"我考虑过 fail-open vs fail-close"就赢了。
- 禁用即时生效：管理员禁用用户时 user 服务写 `user:disabled:{uid}`，网关每请求都查——不用等 7 天 token 过期。

**【一分钟回答】** 登出把 token 写进 Redis 黑名单，TTL 等于剩余有效期，网关验签后查黑名单命中就 401。Redis 故障时 fail-open 保主链路可用。封禁走另一个 disabled 标记 key，实现旧 token 即时失效。

## 知识点 4：微服务间的身份透传链（ThreadLocal + Header + Feign 拦截器）

**【面试怎么问】** 网关鉴权后，下游服务、以及服务调服务时怎么知道当前用户是谁？

**【项目代码】** 一条完整的链，三个组件接力：

```java
// ① 网关验完 JWT, 把身份塞 header 转发
ServerHttpRequest mutated = request.mutate()
        .header("X-User-Id", String.valueOf(uid))
        .header("X-User-Role", String.valueOf(r)).build();

// ② 下游服务入站: HeaderInterceptor 读 header → ThreadLocal
public boolean preHandle(HttpServletRequest request, ...) {
    String userId = request.getHeader("X-User-Id");
    if (StringUtils.hasText(userId)) SecurityContextHolder.setUserId(userId);
    return true;
}
public void afterCompletion(...) {
    SecurityContextHolder.remove();   // ⚠️ Tomcat线程复用, 不清会串号!
}

// ③ 服务调服务出站: FeignAuthInterceptor 从 ThreadLocal 取 → 写回 header
public void apply(RequestTemplate template) {
    Long uid = SecurityContextHolder.getUserId();
    if (uid != 0L) template.header("X-User-Id", String.valueOf(uid));
}
```

**【讲解】**
- 入站拦截器和出站拦截器**完全对称**：入站 header→ThreadLocal，出站 ThreadLocal→header。业务代码只面对 `SecurityContextHolder.getUserId()`，不感知 HTTP。
- `afterCompletion` 里清 ThreadLocal 是必答点：Tomcat 线程池复用线程，不清的话**下一个请求会看到上一个用户的 userId**——这是真实的越权事故模式。
- 例子：下单时 order 服务 Feign 调 user 服务查地址，不用传 userId 参数，拦截器自动续传，user 服务照常校验"这个地址是不是你的"。

**【一分钟回答】** 网关把 userId 放 X-User-Id header；下游 MVC 拦截器进门存 ThreadLocal、出门必清（防线程复用串号）；Feign 请求拦截器出站时再从 ThreadLocal 写回 header，身份就能跨任意多跳传递，业务代码零感知。

## 知识点 5：密码存储与登录安全细节

**【面试怎么问】** 密码怎么存？登录接口有哪些安全考虑？

**【项目代码】** `mini-mall-auth/.../AuthController.java`

```java
private static final BCryptPasswordEncoder ENCODER = new BCryptPasswordEncoder();

// 注册: 只存 BCrypt 密文 (自带随机盐, 同一密码每次密文都不同)
String encryptedPassword = ENCODER.encode(dto.getPassword());

// 登录: ② 防爆破 —— 不区分"用户不存在"和"密码错"
if (user == null || !ENCODER.matches(dto.getPassword(), user.getPassword())) {
    throw new BusinessException("用户名或密码错误");
}
// ②.5 禁用检查放在密码校验【之后】: 密码不对的人连"账号被禁"都不该知道
if (user.getStatus() == 0) throw new BusinessException(403, "账号已被禁用");
// ④ 返回前兜底清密文
user.setPassword(null);
```

**【讲解】**
- BCrypt 慢哈希 + 内置随机盐：彩虹表失效，暴力破解成本高；`matches` 从密文里解析出盐再比对，所以不需要单独存盐字段。
- 错误信息**故意模糊**："用户名或密码错误"不让攻击者探测哪些用户名存在。禁用提示的顺序也是同一思想——信息最小化。
- 登录接口挂了 Sentinel 限流（`@SentinelResource(blockHandler=...)`），防脚本爆破刷接口。

**【一分钟回答】** BCrypt 存密文（慢哈希+随机盐），登录报错不区分用户不存在/密码错防探测，禁用检查放在密码校验后同理，接口本身有 Sentinel 限流防爆破，响应前清掉密码字段。

## 知识点 6：第三方登录（GitHub OAuth2 授权码模式）

**【面试怎么问】** OAuth2 流程说一下？你项目怎么实现的？

**【项目代码】** `mini-mall-auth/.../OAuthController.java`，标准授权码三步：

```java
// ① 给前端拼授权页 URL (带 client_id + redirect_uri + state)
String authorizeUrl = String.format("%s?client_id=%s&redirect_uri=%s&scope=%s&state=%s", ...);

// ② GitHub 回调带 code → 后端拿 code+client_secret 换 access_token
String tokenUrl = String.format("%s?client_id=%s&client_secret=%s&code=%s", ...);
String tokenJson = restTemplate.postForObject(tokenUrl, entity, String.class);

// ③ 拿 access_token 调 GitHub API 取用户信息 → 本地查 oauth_id, 没有就自动建号 → 签自家 JWT
Result<User> findResp = userFeignClient.getByOauth("github", githubUserId);
if (user == null) { /* 首次登录自动注册 gh_xxx 账号 */ }
String token = jwtUtil.generateToken(user.getId(), user.getUsername(), user.getRole());
```

**【讲解】**
- 授权码模式的核心安全点：**access_token 永远不经过浏览器**——浏览器只见 code，code 换 token 发生在后端（需要 client_secret）。
- `state` 参数双重用途：防 CSRF + 项目里顺便 Base64 编码了"登录前想去的页面路径"，登录完跳回原页。`normalizeRedirect` 只允许站内路径（拒绝 `//` 开头），防开放重定向漏洞。
- 三种登录方式（密码/OAuth/邮箱验证码）**返回结构统一**都是 `AuthResponse(token, user)`，前端不用区分。

**【一分钟回答】** 授权码模式三步：前端跳 GitHub 授权页 → GitHub 回调我后端带 code → 后端用 code+secret 换 token 再取用户信息，本地按 oauth_id 找或自动建号，最后签发我们自己的 JWT。state 防 CSRF 且校验 redirect 只能站内，token 交换全程在后端。

## 知识点 7：邮箱验证码登录（Redis 三键设计）

**【面试怎么问】** 验证码怎么设计？怎么防刷防爆破？

**【项目代码】** `mini-mall-auth/.../EmailAuthController.java`，三个带 TTL 的 key：

```java
// auth:email:code:{email}   验证码本体, 5分钟
// auth:email:limit:{email}  60秒重发限制
// auth:email:err:{email}    验错计数, 连错5次作废验证码

// 防刷: SETNX 原子"不存在才放" —— 已存在说明60秒内刚发过
Boolean first = stringRedisTemplate.opsForValue()
        .setIfAbsent(LIMIT_PREFIX + email, "1", 60, TimeUnit.SECONDS);
if (!Boolean.TRUE.equals(first)) throw new BusinessException(429, "发送太频繁");

// 防爆破: 6位数字只有100万种, 连错5次删码逼重发
Long errCount = stringRedisTemplate.opsForValue().increment(ERR_PREFIX + email);
if (errCount >= 5) { stringRedisTemplate.delete(codeKey); throw ...; }

// 验证通过 → 码立刻删除(一次性, 防5分钟窗口内重放登录)
stringRedisTemplate.delete(codeKey);
```

**【讲解】**
- **先存 Redis 再发邮件**：反过来的话"邮件发出去了但存 Redis 失败"，用户拿着收到的码验不过，体验更糟；发送失败还要回滚 limit key 让用户能立刻重试。
- `SecureRandom` 而不是 `Random`：验证码是安全场景，Random 的种子可被推测。
- 未注册邮箱**自动注册**而不是报错：既省流程，又不暴露"这个邮箱注册过没有"（同登录报错模糊化思想）。

**【一分钟回答】** 三个 Redis key 各带 TTL：码本体 5 分钟、SETNX 做 60 秒重发限制、错误计数连错 5 次作废码。码验证通过立即删除保证一次性。顺序上先存 Redis 再发邮件，发送失败回滚限制 key。

## 知识点 8：文件上传安全（魔数校验）

**【面试怎么问】** 文件上传有什么安全风险？怎么防？

**【项目代码】** `mini-mall-file/.../MinioService.java`

```java
// 不信任前端的扩展名和 Content-Type(都能伪造), 只认文件内容开头的魔数
private enum ImageType {
    JPEG(new byte[]{(byte) 0xFF, (byte) 0xD8, (byte) 0xFF}, "image/jpeg", "jpg"),
    PNG(new byte[]{(byte) 0x89, 0x50, 0x4E, 0x47}, "image/png", "png"),
    GIF(new byte[]{0x47, 0x49, 0x46, 0x38}, "image/gif", "gif");
    // 故意不收 SVG: SVG 是 XML 能内嵌 <script>, 放公共读的桶里 = 挂了个 XSS 页面
}

ImageType type = detect(bytes);            // 验魔数: evil.html 改名 a.png 也过不了
if (type == null) throw new BusinessException(400, "仅允许 jpg/png/gif");

// 存储路径用服务端生成的一切: bizType白名单/日期/UUID/检测出的扩展名
String objectName = bizType + "/" + LocalDate.now() + "/" + UUID.randomUUID() + "." + type.ext;
```

**【讲解】**
- 四道防线：bizType 白名单（防 `../` 路径穿越）→ 5MB 业务层限制（不依赖 yml 配置）→ 魔数检测内容真身 → 文件名/扩展名/Content-Type 全部服务端生成，**前端给的信息一个都不采纳**。
- 拒收 SVG 是懂行的表现：SVG 可执行脚本，公共桶里的 SVG 就是存储型 XSS。

**【一分钟回答】** 上传攻击的本质是"文件伪装"，扩展名和 Content-Type 都可伪造，所以只认文件头魔数判断真实类型；存储路径全部服务端生成（白名单目录+UUID+检测出的扩展名）；SVG 因可嵌脚本直接拒收；大小限制在业务层再兜一道。
