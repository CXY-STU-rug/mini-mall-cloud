# 06 事务与数据一致性（本项目含金量最高的一章）

> 一致性手段项目里落地了五种，面试按"问题由轻到重"的顺序讲：
> **单机并发 → CAS 状态机；单库多表 → 本地事务；跨服务强一致 → Seata AT；跨服务最终一致 → MQ/afterCommit；兜底 → 定时对账。**

## 知识点 1：原子状态机（条件 UPDATE / CAS）—— 全项目最重要的一个套路

**【面试怎么问】** 并发下怎么保证订单状态不错乱？比如用户点支付的同一秒 MQ 正好来关单？

**【项目代码】** `OrdersServiceImpl.closeOrderByMQ()`，注释里把竞态推演写得很清楚：

```java
// ⭐ 老写法"读 status 判断 → updateById"在 MQ 消费者里最危险(没有任何锁):
//   时刻T1: MQ 读到 status=0        时刻T1: 用户支付也读到 status=0
//   时刻T2: MQ 改成 4 + 回库存       时刻T2: 支付改成 1  ← 谁后写谁覆盖, 库存还被多回一次
// 改成条件 UPDATE 后: 数据库行锁只让一个 UPDATE 命中(rows=1), 输家 rows=0 安静退出
LambdaUpdateWrapper<Orders> uw = new LambdaUpdateWrapper<>();
uw.eq(Orders::getId, orderId)
  .eq(Orders::getStatus, OrderStatus.UNPAID)      // WHERE 里的"期望旧状态"
  .set(Orders::getStatus, OrderStatus.CANCELLED); // SET 新状态
int rows = ordersMapper.update(null, uw);
if (rows == 0) {
    return;   // 已付款/已取消/重复消息 → 什么都不做(尤其是不能回库存!)
}
// 只有赢家才回库存 + 退券
```

同一套路在项目里的全部落点（面试可任选举例）：

| 状态流转 | 方法 | 并发对手 |
|---------|------|---------|
| 0待付款→1已付款 | payOrder / markPaidByNotify | MQ关单、重复回调 |
| 0待付款→4已取消 | cancelOrder / closeOrderByMQ | 用户支付、双击取消 |
| 1已付款→2已发货 | shipOrder | 两个管理员同时点发货 |
| 2已发货→3已完成 | signOrder | 双击签收 |
| 1/2→5申请退款中 | markRefundApplying | 重复申请 |
| 5→6已退款 | markRefundedByNotify | 重复退款通知 |
| 库存扣减 | `UPDATE product SET stock=stock-? WHERE stock>=?` | 超卖 |
| 券核销 | `UPDATE user_coupon SET status=1 WHERE status=0` | 一券两单 |

**【讲解】**
- 本质是把 **check-then-act 合并成一条原子 SQL**：判断条件从 Java if 挪进 WHERE，由数据库行锁裁决，天然解决"两个并发请求都通过了 Java 判断"的问题。
- `rows` 返回值就是胜负信号：rows=1 我赢了继续做副作用（回库存/退券）；rows=0 我输了**且绝不做副作用**——"不能重复回库存"这句是灵魂。
- 它同时白送幂等：MQ 消息重复投递，第二次 WHERE 不满足 rows=0 直接返回。
- 和乐观锁的关系：这就是乐观锁思想（期望值做条件），只是用业务状态字段而不是 version 字段。

**【一分钟回答】** 所有状态流转都写成 `UPDATE ... SET 新状态 WHERE id=? AND status=旧状态` 的条件更新，把判断塞进 WHERE 让数据库行锁裁决并发。rows=1 才执行后续副作用，rows=0 静默退出。一个套路同时解决并发覆盖、重复点击、消息重复三个问题。

## 知识点 2：本地事务的边界控制（@Transactional vs TransactionTemplate）

**【面试怎么问】** @Transactional 有什么坑？什么时候不用注解用编程式？

**【项目代码】** `OrdersServiceImpl.createOrder()`：

```java
// 注解事务的边界=整个方法, 但发MQ必须在事务提交后 → 用编程式精确划界
Map<String, Object> orderResult = transactionTemplate.execute(status -> {
    ... 建单/用券/存明细/扣库存/清购物车 ...
    return result;
});   // ← 到这里事务已提交
rabbitTemplate.convertAndSend(DELAY_EXCHANGE, DELAY_ROUTING_KEY, orderId);  // 事务外发MQ
```

**【讲解】**
- 选编程式的理由就一个：**事务边界要比方法边界小**。注解版整个方法都在事务里，发 MQ 也被卷进去 → 幽灵消息（见 05）。
- @Transactional 常见坑清单（结合项目答）：① 同类内部调用不生效（AOP 代理绕过）；② 默认只回滚 RuntimeException，项目里全部显式 `rollbackFor = Exception.class`；③ 事务内做远程调用/发消息的时序问题（本项目的核心实践点）。
- MQ 消费者里也用 `transactionTemplate.execute(...)`（SeckillOrderListener）：消费方法本身不能整个是事务——ACK/NACK 和补偿逻辑必须在事务外。

**【一分钟回答】** 注解事务简单但边界固定为整个方法；当需要"事务提交后再做某事"（发 MQ、调外部系统）时用 TransactionTemplate 手动划界，把这些操作放在 execute 返回之后。另外注意 rollbackFor 要显式写 Exception.class，内部调用不走代理等经典坑。

## 知识点 3：跨服务分布式事务（Seata AT 模式）

**【面试怎么问】** 下单要扣 product 库的库存，order 库的事务回滚了 product 怎么办？

**【项目代码】** `OrdersServiceImpl.createOrder()` 方法头：

```java
@GlobalTransactional(name = "createOrder-tx", rollbackFor = Exception.class)
public Map<String, Object> createOrder(Long userId, CreateOrderDTO dto) {
    // ⭐ G5: Seata TM 在这分配全局 XID
    //   - Feign 自动透传 XID 到 product
    //   - product 扣库存写 undo_log, 一阶段本地提交
    //   - 本方法抛任何异常 → TC 反向通知 product 走 undo_log 回滚 stock
```

**【讲解】**（AT 模式两阶段，结合项目流程讲）
- **一阶段**：product 执行扣库存 SQL 时，Seata 数据源代理自动记录前后镜像到 `undo_log` 表，然后**本地事务直接提交**（不长期占锁，这是 AT 比 XA 快的原因）。
- **二阶段**：order 全流程成功 → TC 通知各分支异步删 undo_log；order 抛异常 → TC 通知 product 用 undo_log 反向补偿（把库存加回去）。
- XID 靠 Feign 拦截器自动透传，业务代码只加一个注解——这是 AT 的"无侵入"卖点。
- **诚实的局限**（项目注释原文，面试主动讲）：user 服务没接 Seata，用券成功但后续扣库存失败时，`user_coupon` 的变更不会自动回滚——所以取消/退款路径上另有 `refundCoupon` 补偿调用。真实系统就是这样**混合使用**：核心链路 Seata，外围补偿。

**【一分钟回答】** 下单方法加 @GlobalTransactional，Seata AT 模式：分支事务一阶段本地提交但记 undo_log，全局失败时 TC 通知各分支按 undo_log 反向补偿。XID 通过 Feign 自动透传。我们只把 order↔product 强一致链路交给 Seata，优惠券走 MQ/接口补偿——按重要性分级选一致性方案。

## 知识点 4：afterCommit 事务同步钩子（跨服务调用的时机问题）

**【面试怎么问】** 事务里调其他服务的接口有什么问题？

**【项目代码】** `OrdersServiceImpl.cancelOrder()` 退券：

```java
// afterCommit 原因: user 端如果立刻回查 orders 表确认状态,
// 此时 UPDATE 还没 commit, 它看不到 CANCELLED → 判断错误
Long ucId = order.getUserCouponId();
if (ucId != null) {
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            userFeignClient.refundCoupon(ucId);   // 事务提交后才通知 user 退券
        }
    });
}
```

**【讲解】**
- 问题本质是**事务可见性**：我还没 commit，远程服务读我的库（或经我的接口读）看到的是旧数据。把远程调用挂到 afterCommit，保证对方看到的世界和我承诺的一致。
- 代价：afterCommit 里失败**不会回滚已提交的本地事务**，所以只适合"允许补偿"的操作（退券失败可对账修），不适合强一致操作。
- 和"事务外发 MQ"是同一思想的两种实现，一个用于 MQ 一个用于 Feign。

**【一分钟回答】** 事务内做远程调用，对方可能读到未提交的旧状态，且远程调用的耗时会拉长事务持锁时间。解法是 TransactionSynchronization 的 afterCommit 钩子，提交后再调；代价是钩子里失败无法回滚本地事务，所以只放可补偿的操作。

## 知识点 5：优惠券防超发/防重复（多层防御的标准样板）

**【面试怎么问】** 领券怎么防止超发？怎么防一人多领？

**【项目代码】** `mini-mall-user/.../CouponServiceImpl.receive()`：

```java
// Step 2: 应用层查重(第一道, 挡住99%)
long had = userCouponMapper.selectCount(...userId+couponId...);
if (had > 0) throw new BusinessException("您已领取过该券");

// Step 3: CAS 扣库存 —— UPDATE coupon SET remain_stock=remain_stock-1 WHERE id=? AND remain_stock>0
int rows = couponMapper.deductRemainStock(couponId);
if (rows == 0) throw new BusinessException("券已领完");

// Step 4: INSERT user_coupon
// ⭐ 数据库 UNIQUE KEY(user_id, coupon_id) 是兜底:
//   高并发下 Step2 可能漏掉一个, 此处 INSERT 抛 DuplicateKeyException
//   → Spring 事务自动回滚, Step3 扣的库存也一起回滚(同一事务)
userCouponMapper.insert(uc);
```

**【讲解】**
- 三层防御：**应用层查重（快速失败）→ CAS 扣库存（防超发）→ 唯一索引（防重复领的最后防线）**。前两层是性能优化，唯一索引才是正确性保证。
- 最精彩的联动：第 4 步唯一索引冲突抛异常 → 同一个 `@Transactional` 里第 3 步扣掉的库存**自动回滚**——库存和领取记录的一致性由本地事务免费保证。
- 用券 `useCoupon` 同样是 CAS（`WHERE status=0`），防同一张券被两个并发订单同时用。

**【一分钟回答】** 三层：应用层先查重快速拒绝；库存用 `WHERE remain_stock>0` 的 CAS 扣减防超发；(user_id,coupon_id) 唯一索引兜住并发穿透查重的漏网请求，冲突异常触发事务回滚把扣掉的库存还回去。正确性的底线永远压在数据库约束上。

## 知识点 6：定时对账补偿（最终一致的最后一道网）

**【面试怎么问】** 支付回调通知 order 服务失败了怎么办？（跨服务调用失败的最终兜底）

**【项目代码】** `mini-mall-payment/.../task/PaymentReconciliationTask.java`：

```java
@Scheduled(initialDelayString = "${...:30000}", fixedDelayString = "${...:60000}")
public void reconcilePaidPayments() {
    // 找出 payment.status=1(钱已到) 的最近100条, 逐个核对 order 状态
    // 若 order 还是待付款(0) → 补一次 markPaid
    Result<Boolean> markResp = orderFeignClient.markPaid(orderId);
}
```

配套的设计在 `PaymentServiceImpl.applyPaid()`：

```java
// ⚠ 通知 order 失败时【不回滚支付单】(钱确实到了), 只 log, 靠对账 job 补 markPaid
try { orderFeignClient.markPaid(payment.getOrderId()); }
catch (Exception e) { log.error("[pay-paid] 通知 order 异常, 待对账补偿", e); }
```

**【讲解】**
- 关键决策：支付单已改"已支付"后通知 order 失败，**不能回滚支付单**——钱是客观事实，系统状态必须向事实收敛，而不是把事实改掉。不一致窗口交给对账任务闭合。
- 对账逻辑安全的原因：`markPaid` 本身是 CAS（WHERE status=0），补偿重复执行也无副作用——**对账 + 幂等接口**是黄金搭档。
- 这是"最终一致"的完整叙事收尾：同步重试（没做）→ 异步补偿（对账 60 秒一轮）→ 人工介入（日志留痕）。

**【一分钟回答】** 支付成功但通知订单失败时不回滚支付单（钱到账是事实），记日志后由定时对账任务兜底：每分钟扫"支付单已支付但订单仍待付款"的不一致数据，重放 markPaid。因为 markPaid 是 CAS 幂等的，补偿可以无脑重试。

## 附：MyBatis-Plus 在项目里的使用要点

- **分页插件**：各服务 `MybatisPlusConfig` 注册 `PaginationInnerInterceptor`，`this.page(pageObj, wrapper)` 自动拼 LIMIT + count。
- **逻辑删除**：`is_deleted` 字段全局配置，`removeById` 实际是 UPDATE，查询自动过滤。
- **LambdaQueryWrapper/LambdaUpdateWrapper**：方法引用代替字符串列名，编译期检查防手误；条件 UPDATE 全靠 LambdaUpdateWrapper 的 `.eq(...).set(...)`。
- **自增回填**：`this.save(order)` 后 `order.getId()` 直接可用（订单明细要用它）。
- **N+1 优化**：订单列表先 `IN` 批量查全部明细，再 `computeIfAbsent` 按 orderId 分组组装，两条 SQL 替代 N+1 条。
